# Scenario Bundle - odd_sdlc Software-Domain Worksite Lifecycle

**Validates**: REQ-F-ODDSDLC-009, REQ-F-ODDSDLC-010, REQ-F-ODDSDLC-011, REQ-F-ODDSDLC-012, REQ-F-ODDSDLC-013, REQ-F-ODDSDLC-014, REQ-F-ODDSDLC-015, REQ-F-ODDSDLC-016, REQ-F-ODDSDLC-017

**Purpose**: Prove that `odd_sdlc` can govern a software project as a full SDLC
worksite rather than only as a bootstrap-to-release toy: one bounded software
request is gated, specified, designed, realized, qualified, released, deployed,
observed, brought back with runtime evidence, and reopened lawfully for
retrofit and relaunch.

## Scenario

Create or use a bounded workspace governed by `odd_sdlc`, then carry one
software request through the full domain lifecycle under the same governing
line:

- request capture and gate decision
- specification and design derivation or refinement
- implementation realization through generated, adopted, imported, repaired, or
  retrofitted work
- qualification and testcase-authority proving
- release assembly and deployment
- runtime observation and evidence return
- retrofit planning and relaunch

The proving lane may use a mixed-provenance project where some software truth is
imported or adopted rather than freshly generated, provided those acts remain
explicit in provenance and bound to the same governed asset graph.

## Significant Paths

- software-domain path: `odd_sdlc` is exercised as the generic software-domain
  package rather than only as the bootstrap toy tenant
- worksite path: the project remains a governed worksite across release and
  return rather than ending at the first release narrative
- asset-ontology path: request, implementation, qualification, release,
  deployment, runtime-observation, and retrofit assets are all visible as domain
  assets
- provenance path: generated, adopted, imported, repaired, retrofitted,
  released, deployed, and returned work acts are distinguishable in attributable
  history
- edge-contract path: each open edge is explainable through declared source
  assets, target asset, transform dependency, evaluator dependency, work-report
  contract, proof policy, and closure policy
- generic-software path: configured `F_P` performs the constructive traversal
  for generic software-domain edges under an explicit work-report contract
- layered-F_D path: `Core F_D`, optional `Capability F_D`, mandatory
  `Postflight F_D`, and `Operational F_D` are all visible at the correct
  boundary
- runtime-return path: deployment or execution evidence comes back into the same
  governed line as a lawful input to repair or retrofit work
- relaunch path: a returned-runtime finding can open a new bounded cycle that
  leads to a new release or maintenance release without leaving the governed
  line
- substrate-boundary path: ABG remains authoritative for runtime fact truth
  while software-domain semantics remain tenant-owned

## Expected Outcomes

1. `odd_sdlc` is explainable as the software-domain package on the `odd_sdlc`
   line rather than only as a bootstrap proving toy
2. one bounded software request can be traced through request, gate, specify,
   design, implement, qualify, release, deploy, observe, return, retrofit, and
   relaunch acts
3. the governed asset graph includes software-lifecycle assets beyond the
   bootstrap subset
4. imported or adopted software truth is not conflated with freshly generated
   truth
5. generic software-domain traversal uses configured `F_P` to modify actual
   governed artifacts rather than only to narrate completion
6. deterministic authority is visible in layered form before and after
   constructive traversal
7. runtime-returned evidence can reopen governed work without creating a second
   runtime or a second product authority
8. any required substrate fixes remain expressible in generic runtime or hook
   terms rather than in software-delivery-specific artifact names

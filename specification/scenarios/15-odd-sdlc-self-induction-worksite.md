# Scenario Bundle - odd_sdlc Self-Induction Worksite

**Validates**: REQ-F-ODDSDLC-034

**Purpose**: Prove that released odd_sdlc can govern mutable odd_sdlc source
development through an installed worksite lane without collapsing source
project, released product, installed payload, and mutable worksite identity.

## Scenario

Create a mutable odd_sdlc-like source workspace whose declared realization root
is already source-style, then install released odd_sdlc into that workspace and
operate it through installed odd_sdlc surfaces.

The proving lane must show:

- the installed payload lands under `.genesis/odd_sdlc/`
- the mutable project realization remains under its declared
  `build_tenants/...` output root
- installed query and gap surfaces attribute source traceability to the mutable
  project realization root rather than to the installed payload

## Significant Paths

- self-induction path: released odd_sdlc governs mutable odd_sdlc source
  development without special self-host shortcuts
- topology path: `.genesis/odd_sdlc/` and the mutable project realization root
  stay distinct
- traceability path: requirement/code attribution points at the declared source
  realization root
- operator path: installed `query-domain` and `gaps` operate over the mutable
  self-induction worksite

## Expected Outcomes

1. released odd_sdlc can govern mutable odd_sdlc source development through an
   installed worksite lane
2. installed payload and mutable project realization remain distinct filesystem
   boundaries
3. installed query and gap surfaces read the source realization root as project
   truth rather than reading installed payload files as the governed code line
4. odd_sdlc applies to itself the same source/install/product/worksite law it
   applies to downstream governed projects

# B-068: Isolate Test35 Recursive Realization Deepening In TS

## Lead

This ticket is about the capability test35 proved: repeated lawful
realization over the same graph edge until the product became domain-shaped and
execution-backed.

The defect is not "test45 has fewer files" by itself. The defect is that the
current line can close a realization edge without proving recursive deepening,
required domain inventory, behavioral test inventory, or governed test
execution evidence.

## Product Consequence

`data_mapper.test35` generated the core of the enterprise solution: compiler,
resolver, executor, synthesis, manifest, assurance, accounting, fidelity, and
engine responsibilities with behavioral tests and execution evidence.

That is the distinction between vibe coding and solution delivery.

Vibe coding can produce plausible artifacts. Solution delivery requires a
governed path from requirements to domain-shaped implementation, behavioral
tests, runtime evidence, lineage, and repeatable closure. Test35 showed that
the SDLC line can cross that boundary when iterative realization is working.

This ticket exists to preserve that boundary in the TypeScript/ODD line. The
success criterion is not larger output. The success criterion is governed
construction of the enterprise core through ABG-managed traversal and
evidence-backed convergence.

## Root Capability

Name: `ABG-governed realization-edge continuation`

This is the root capability that must be isolated and proven.

```text
Compute.Iterate(edge, current_state)
  -> Transform via F_D/F_P
  -> Evaluate via F_D/F_P/F_H
  -> if unresolved: record gap evidence
  -> re-enter the same edge with current_state + prior evidence + obligations
  -> repeat until convergence, escalation, or bounded stop law
```

The shorter operational name is `realization-edge recursive deepening`.

The capability is not "generate more files." The capability is lawful
continuation over a realization edge when the current artifact is still
structurally or semantically incomplete.

## Prompt And Evaluator Analysis

A tuned prompt and F_P evaluator should drive the semantic pressure, but they
are not sufficient as the control mechanism.

The prompt can instruct the worker to inspect current state, deepen the target
artifact, preserve obligations, and reduce unresolved gaps. The F_P evaluator
can judge whether the result is semantically shallow, partial, or domain
incomplete. The F_D evaluator can reject missing inventory, absent reports,
trace-only artifacts, broken contracts, or shallow source/test surfaces.

But ABG must own the runtime consequence of those evaluations:

```text
F_D/F_P/F_H says unresolved
  -> ABG records the failed evidence
  -> ABG denies closure
  -> ABG schedules lawful re-entry of the same realization edge
  -> ABG carries state, obligations, provenance, and prior evidence forward
```

If continuation exists only inside the prompt, then the continuation is hidden
inside the LLM's internal traversal. That is not governed ODD compute. It is
unobservable control flow.

Therefore the correct split is:

- Prompt: guides the F_P worker on how to construct and deepen.
- F_P evaluator: judges semantic sufficiency and domain completeness.
- F_D evaluator: enforces deterministic inventory, evidence, reports, syntax,
  contracts, and shallow-output rejection.
- F_H evaluator: applies human or higher-order judgment where policy requires
  it.
- ABG: owns iteration, re-entry, continuation, events, provenance, stop law,
  and closure denial.
- odd_sdlc.TS: defines graph functions, typed carriers, domain inventories,
  evaluators, hook contracts, and proof interpretation.

## Current Capability State

The current TypeScript line isolates and proves the capability:

- graph-function publication
- hook contracts
- F_D/F_P evaluator slots
- gap and query projections
- requirement closure surfaces
- sandbox proof infrastructure
- explicit hook closure policy for ABG retry-repair on unresolved outcomes
- test35-derived CDME capability inventory
- deterministic shallow-output rejection
- governed build/test evidence requirements

The full operational Python replacement claim remains T-041/RC scope. B-068
closes the recursive realization capability as a refactor verification gate,
not as a live external `data_mapper` generation claim.

Test35 had the capability emergently through the Python-era control loop,
prompt pressure, and evaluator pressure. That was productive but not cleanly
isolated. The TypeScript repair must make the capability explicit,
governable, and ABG-native.

### T: Ticket Method

This ticket supersedes B-067 only for the recursive realization capability.
B-067 remains historical closure for the weaker "not pure trace shell" repair.

T-041 remains the wider operational replacement lane. T-041 cannot close while
this capability remains unproven.

### D: Design Module Method

The design must show the module relation:

- ABG owns traversal, continuation, re-entry, runtime facts, lineage, and
  provenance.
- GTL graph functions remain the constructive carrier.
- odd_sdlc.TS owns domain assets, domain hook contracts, domain evaluators, and
  proof interpretation.
- imperative code is bounded adapter code around those surfaces.

The design must not hide this as a service loop or CLI retry wrapper.

### O: ODD Method

The desired shape is outcome-first:

```text
current workspace state
  -> graph-function realization edge
  -> F_D/F_P/F_H evaluation
  -> ABG-authorized re-entry when unresolved
  -> convergence proof
```

The SDLC product configures the allowable traversal space. ABG performs the
runtime traversal.

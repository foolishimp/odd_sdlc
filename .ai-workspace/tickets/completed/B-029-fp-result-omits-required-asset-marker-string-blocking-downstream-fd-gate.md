## Observation

`dmt.test35_r001` observed one pass where `derive_test_run_archive_surface`
failed F_D check `test_run_archive_dependency_surfaces_present` because
`40-generated-test-modules.md` was missing the generated-asset marker string:

```
This test module surface is regenerated by the bounded odd_sdlc constructor turn.
```

`workspace_assets.py:ASSET_MARKERS["test_module_surface"]` defines this as the
required marker, and `_text_contains(marker_path, marker_text)` certifies it.

But the original ticket framing overstated the gap. Current odd_sdlc already:

- certifies generated assets by marker in `workspace_assets.py`
- injects the same marker on constructor prompts in `constructor.py`
- currently produces a `dmt.test35_r001` `40-generated-test-modules.md` that
  does contain the marker

So the remaining issue is not “requirements forgot to say the marker exists.”
The remaining issue, if it persists across F_P paths, is prompt/certification
drift inside the realization design.

## Why The Original Triage Was Wrong

The original ticket claimed the marker string was not mentioned anywhere in the
generation contract and therefore the LLM had no way to know it must be
present.

That is no longer true in current odd_sdlc.

The constructor path already injects `asset_marker("test_module_surface")`
directly into the generated text contract. So the live problem space is not a
constitutional requirements gap. It is parity between:

- generated-asset certification law
- constructor prompt contract
- probabilistic asset-generation prompt contract

## Required Direction

1. Publish one design-level marker contract shared by:
   - generated-asset certification in `workspace_assets.py`
   - constructor prompt generation
   - probabilistic asset-generation prompt generation
2. Make one path authoritative:
   - either marker text is injected by the framework before certification
   - or every probabilistic asset-generation prompt explicitly carries the same
     marker instruction as constructor paths
3. Remove the current requirement-level framing. This is not constitutional
   product law; it is generated-asset realization design.

## Acceptance

- generated-asset certification and asset-generation prompts consume one marker
  contract
- constructor and probabilistic asset-generation paths cannot drift on marker
  requirements
- a ticket like `dmt.test35_r001` no longer needs to frame this as a missing
  requirements-layer truth

## Completion

- generated-asset marker text now lives in the shared
  `GeneratedAssetContract` published by
  `build_tenants/python/code/odd_sdlc/workspace_assets.py`
- workspace asset publication now carries the same generated-asset contract
  through the query surface, including marker text, marker path, heading
  prefix, and file/member requirements where applicable
- `genesis.binding._assemble_prompt(...)` now renders that published
  generated-asset contract into the F_P prompt, so prompt-side target
  requirements come from the same contract that deterministic certification
  uses
- constructor marker injection now remains on the same truth path because
  `asset_marker(...)` resolves through `generated_asset_contract(...)` instead
  of a prompt-local string surface
- focused proof:
  - `test_bootstrap_asset_publication_shares_generated_asset_contract_with_fd_certification`
  - `test_probabilistic_prompt_uses_published_generated_asset_contract_for_target_asset`
  - `test_ticket_asset_start_carries_ticket_execution_context_into_manifest_prompt`
  - `test_install_query_domain_publishes_triaged_work_item_asset_and_route_contract`
  - `test_install_start_routes_ticket_asset_without_manual_upstream_edit`

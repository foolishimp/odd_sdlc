# Post-Closure Review: Completed Active-Wave Tickets Against ODD_METHOD Graph Requirements

## Scope

Reviewed completed tickets:

- `T-021`: publish constructive prompt template / prompt provenance
- `T-023`: admit ticket-shaped execution contracts before work executes
- `B-034`: public `odd_sdlc start` honors ambiguity F_H escalation
- `T-022`: publish one gap-analysis dossier surface

This review does not reopen tickets. It records whether their closed state is
coherent with ODD_METHOD graph-native requirements and names residual risks
that must not be mistaken for closure evidence in later work.

## Review Basis

ODD_METHOD graph requirements applied:

- typed assets and nodes are explicit
- operative constructive steps are carried by named `GraphFunction` or lawful
  graph-function composition
- function catalog is machine-readable
- GTL module publishes callable carriers, graphs, typed nodes/vectors, jobs, and
  refinement boundaries
- projections expose current state over constructive history and must not become
  rival runtime truth
- product-specific semantics sit above GTL/ABG structural law
- manual walkthrough remains lawful
- graph functions declare cumulative environment requirements/provisions/carry
- local and refined closure agree under zoom
- proof lanes exercise install, traversal, evidence, and target-relative closure

TICKET_METHOD migration criteria also applied for source-carrier tickets:

- replace control-flow-owned meaning with carrier/event/algebra-owned truth
- remove hidden semantic centers rather than wrapping them
- consume typed/admitted carriers directly rather than reconstructing from raw
  text, `.get(...)`, fallback config, or legacy read models
- include mixed-state negative proof where a legacy path could otherwise pass

## Cross-Ticket Architecture

The closed wave is coherent only when read in this order:

1. `T-021` is historical prompt-pressure work. Its original "domain-owned
   constructive prompt template" implementation shape is no longer current
   runtime law.
2. `T-023` supersedes that shape by admitting `execution_contract_surface` as
   the source carrier and carrying it through ABG 3.2 prompt contexts.
3. `B-034` makes ambiguity policy a graph-carried F_H/F_P regime decision
   visible to public `odd_sdlc start`.
4. `T-022` is downstream: it publishes a dossier projection over current
   gap/triage/route truth and must not replace the admitted execution contract.

That order satisfies the ODD_METHOD rule that source carriers land before
downstream projections and prompt/report consumers.

## B-034 Review

Ticket:
`.ai-workspace/tickets/completed/B-034-public-odd_sdlc-start-does-not-honor-ambiguity-fh-escalation.md`

Verdict:
ODD_METHOD graph requirements satisfied for the public-start ambiguity gate.

ODD_METHOD assessment:

- Typed asset/node requirement: pass. The ambiguity register is a published
  domain asset with entries carrying class, status, policy action, blocking
  state, and resolving edge.
- GraphFunction carrier requirement: pass. Ambiguity-governed leaf graph
  functions are cloned with dynamic F_H evaluators when policy requires
  escalation.
- Function catalog/GTL publication: pass. Ambiguity policy start functions and
  `CandidateFamily` entries are published so public `graph_function:` targeting
  can reach the ambiguity-governed edge.
- Current-state projection law: pass. Query-domain, ambiguity register, start
  result, and event stream all read from the same ambiguity source truth.
- Product-specific semantics above shared carrier: pass. odd_sdlc decides
  ambiguity risk policy; ABG carries the F_H/F_P regime effect.
- Manual walkthrough: pass. A human can inspect the ambiguity register, identify
  the resolving edge, inspect the published handle, run public start, and see
  `fh_gate_pending` only when policy says escalation is blocking.
- Cumulative environment law: pass for this scope. The ambiguity policy is
  attached to the graph-function vector and carried into regime evaluation.
- Zoom-stable closure: pass. Low-risk closes to F_H gate; high-risk permits F_P
  carriage without claiming ambiguity resolved.
- Negative proof: pass behaviorally. Low-risk proves public start cannot
  continue through a blocking ambiguity; high-risk proves F_P can still carry
  nonblocking ambiguity.

Findings:

- No closure-blocking ODD_METHOD finding.
- Minor metadata precision issue: `CandidateFamily.policy_hints` uses
  `selection_reason: ambiguity_fh_gate` for all ambiguity-policy start
  functions, while high-risk entries are policy edges but not F_H gates. This is
  not a behavioral closure defect because the dynamic F_H evaluator is only
  attached for `policy_action=escalate_fh`, but the metadata should eventually
  say `ambiguity_policy_edge` or distinguish F_H gate vs F_P carry.

Post-close requirement:

- Keep ABG F_H regime priority as part of the closure proof. If a future ABG
  runtime change reprices F_H/F_P priority, B-034 must be revalidated even
  though odd_sdlc graph publication remains correct.
